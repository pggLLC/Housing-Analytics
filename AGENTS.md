# AGENTS.md — Housing-Analytics

Instructions for AI coding agents (OpenAI Codex, GitHub Copilot coding agent, Claude) working in this repo. Codex reads this file automatically (Copilot would too, but see the pipeline note below — it is not active here); `.github/copilot-instructions.md` (the 18 governance rules) remains authoritative and this file defers to it on data-integrity matters.

## What this repo is
A public-interest **static site** for Colorado affordable-housing data, deployed on **GitHub Pages** (custom domain `cohoanalytics.com` via CNAME). No bundler — client JS attaches to `window.*` via hand-ordered `<script>` tags. Build/fetch scripts are `.mjs` + Python; most workflows are crons that fetch data and commit it back. Exact counts live in the CI-enforced inventory line below — read them there, not from prose.

## Traps that will hand you a red CI
- **Place pages do not auto-regenerate.** Edit the template in `scripts/hna/build_place_pages.py` and rerun it — never hand-edit `places/*.html`, or `test:place-pages-fresh` fails.
- **`ranking-index` and `ranking-scenarios` are coupled.** Regenerating the index without rebuilding scenarios fails `ci-checks` on the pinned `generatedAt`.
- **Brief ownership sections are auto-generated mid-suite.** A brief failure that appears only under full `test:ci` (and passes in isolation) is real, not a flake.
- **A PR failing on files it never touched** usually means `main` broke after you branched. Rebase before debugging your own diff.
- **The source-URL sweep blocks on the URLs your PR adds, and only those.** Two invocations run on a PR, both in `ci-checks.yml`: the changed-files one (`--diff-added --base-ref origin/$base_ref`) is blocking, because a URL you introduce is yours to get right; the full-repository one later in the same job is `continue-on-error: true`, because rot in a citation you never touched is not your PR's problem. A third invocation — the standalone `sweep` workflow — used to run on `pull_request` with paths `js/**/*.js` and `**/*.html`, which hard-blocked nearly every PR on all ~180 external citations; it now runs weekly and on dispatch only (#1545). Existing rot surfaces on the Monday cron, which opens a tracking issue.
- **The sweep retries a 5XX or a network failure once before reporting it** (#1545), so a momentary outage no longer fails a PR. A persistent failure is reported with `(confirmed on retry)`. 404 and 403 are not retried. Do not "fix" a flapping host by adding it to `ALLOW_LIST` — it works most of the time, so suppressing it hides the day it breaks for real.
- **`CLEAN` / `MERGEABLE` does not mean CI passed.** Draft PRs never run `ci-checks`, and any commit carrying the CI-skip directive (every data cron does) skips it too. Read the individual check list and confirm `ci-checks` actually appears — not `mergeStateStatus`. Two PRs merged on 2026-08-16 broke `main` exactly this way, and a third on 2026-08-19 showed `CLEAN` with **zero** workflow runs.
- **A run can be waiting for a human to approve it, and that looks like no run at all.** `gh pr view` shows the PR with only its CodeQL checks and no `ci-checks`, indistinguishable from a skip. The tell is only visible per-run: `gh run list --branch <branch>` reports the conclusion as `action_required`. #1548 sat that way from 2026-09-06 to 2026-09-09 — its runs from five days earlier had succeeded, so nothing looked broken. Approve with `gh api -X POST repos/pggLLC/Housing-Analytics/actions/runs/<id>/approve`, having first checked what the branch would execute. This is the fourth way CI silently does not run, alongside draft PRs, the skip directive, and conflicting PRs.
- **Writing the CI-skip directive in a commit message triggers it — even in prose.** On 2026-08-19 a commit whose body *explained* that data crons use `[skip` `ci]` had every workflow suppressed on that branch: `CLEAN`, no checks, nothing pending. GitHub matches the literal string anywhere in the message, including inside an explanation of it. Describe the directive, never quote it.
- **`npm test` rewrites tracked files while it runs.** It deletes and regenerates all ~480 files under `data/hna/jurisdiction-metrics-digest/` and rewrites several `data/jurisdiction-briefs/*.json` in place. Mid-run `git status` looks like catastrophic data loss. It self-restores — do not "recover" those files and do not commit them. After the run: `git checkout -- data/`.
- **`npm run test:briefs` is only the Python validator.** It does not cover `test/jurisdiction-brief-metric-digest-sections.test.mjs`. If you change brief wording, run the full `npm test` — the targeted script passing is not evidence. This gap shipped a broken `main`.
- **Rebuild `data/manifest.json` only on a clean tree — and delete the iCloud duplicates immediately first.** `scripts/rebuild_manifest.py` walks the **filesystem**, not git. This repo lives under an iCloud-synced directory that accumulates duplicates (`08001 2.json`, `08001 3.json`, …); rebuilding with those present inflated the manifest from 1,607 to 3,573 entries and fails CI on a fresh clone. A clean `git status` does **not** rule this out — the duplicates are *gitignored* (`.gitignore:60-62`), so git never shows them however you ask. **They come back.** On 2026-09-05 the same worktree accumulated 81, then 684, then 54 within a few hours; a rebuild between the second and third inflated the manifest to 2,195 entries, and one of them also broke `test:ci` with a `582 !== 546` digest count. Cleaning once is not enough — run this *immediately* before every rebuild, not at the start of the task. Note the second pattern: iCloud also makes **extensionless** duplicates of directories (`dist/docs 2`, `dist/css 3`), which the original `* [0-9].*` form missed — one of them, `dist.lock/owner 2`, is not even gitignored and turned up staged for commit (#1563):
  ```bash
  find . -path ./node_modules -prune -o \( -name "* [0-9].*" -o -name "* [0-9]" \) -delete
  ```
  Then verify the result rather than trusting it: the entry count must match `main` (`node -e 'console.log(Object.keys(require("./data/manifest.json").files).length)'`). A number larger than main's is the tell.
- **There are two manifests, and the order you rebuild them in matters.** `data/_manifest.json` (built by `npm run audit:file-manifest`) must be regenerated **first**, then `data/manifest.json` (`python3 scripts/rebuild_manifest.py`) — because the second records the byte count of the first. Do it the other way round and `test:file-manifest` fails with `data/manifest.json byte counts are stale — run python scripts/rebuild_manifest.py`, which is the command you just ran. The message names the wrong file and sends you in a loop. Any change to a file under `data/` needs both, in that order (#1563). Note also that `python` is not on PATH in this environment — `python3 scripts/rebuild_manifest.py` silently does nothing as `python`, and the entry count is unchanged, which looks like a successful no-op rebuild.
- **Never `git stash pop` here.** Dozens of worktrees share one stash stack, and a failed `git stash push <path>` still lets a chained `pop` apply another session's stash into `data/`. Copy the file to `/tmp` instead.
- **Do not merge to `main` while a long data build is running.** `build-hna-data.yml` runs ~36 minutes and rebases its data commit at the end; a merge touching `data/manifest.json` inside that window kills the whole run with a rebase conflict. Check for in-flight runs before merging.
- **A cron time is not an arrival time — add about three hours.** Measured across 49 scheduled workflows and ~8 recent runs each (#1555): GitHub starts every one of them late, **median ~180 minutes**, and never near zero. `fetch-fred-data` at `0 6 * * *` has not once started less than 265 minutes late. Day-of-week, by contrast, is honoured exactly (18 of 18 sampled Monday crons started on a Monday). So schedule by day and by a rough window, never by a clock time, and set the cron ~3h before you want the result to land. The schedule is tuned so every committing workflow lands 00:00–05:00 Mountain, in the trough of the owner's own commit activity — if you move one, keep it there. Two contributing causes are inside this repo's control and are already fixed: 38 of 55 crons fired at minute `:00`, and several fired in the same minute as each other. Keep new crons off `:00` and off a minute another workflow already uses.
- **`data/hna/place-chas.json` is rebuilt by `build-hna-data.yml` Phase 6.4, and the
  order is load-bearing.** `build_place_chas.py` anchors place household counts to
  ACS occupied units by reading `data/hna/summary/`, so it must run *after* the ACS
  phases and Phase 2.5, and *before* Phase 7 (the ranking index reads it). Nothing
  rebuilt this file at all before 2026-09-10 — it was last built by hand on
  2026-07-14 and drifted from the summaries on every ACS refresh, surfacing as an
  unrelated PR failing CI on files it never touched. `test:place-chas-fresh` now
  fails on drift.

- **`cancelled` on a data workflow usually means it hit `timeout-minutes`.** It renders grey, not red, so nothing alerts and a scan for failures misses it entirely. `build-hna-data` went 15 days with no completed scheduled run this way ([#1556](https://github.com/pggLLC/Housing-Analytics/issues/1556)) while every check stayed green. Compare a run's duration against the timeout before reading `cancelled` as "someone stopped it".

## Green is not the same as verified
A passing check list answers "did the jobs report success", not "did the work happen". These four questions are not answered by reading a diff, and a code review will not surface them. Check them yourself before treating a PR as verified.

- **Did the check actually run?** A workflow that never triggered is not a pass. Path filters are the usual cause: a change to `.github/workflows/**` runs only the workflows whose own `paths:` include that prefix. On 2026-08-19 a PR touching five audit workflows triggered three of them — `contrast-audit`'s filters are `css/**`, `**/*.html`, `js/**`, and `console-error-audit` has no `pull_request` trigger at all. Both have `workflow_dispatch`; dispatch them on the branch rather than assuming.
- **Did the passing test assert anything?** A workflow that skips its work also reports green. Read the run log for evidence of real output — `chart-audit` prints per-page chart counts (`… 11/11 OK`), and an audit that rendered nothing still exits 0.
- **`cancelled` is a failure mode, not a neutral outcome.** A hung step is killed by the job timeout and recorded as `cancelled`, which renders grey rather than as a red X. Scanning for red misses it. Worse, the timeout is not reliable: on 2026-08-19 a job with `timeout-minutes: 30` was still `in_progress` at 232 minutes.
- **Is `main` itself green right now?** Data crons suppress CI on their own commits, so `main` can be broken for hours with no failing run to show for it. A PR failing on files it never touched is the usual first symptom — check `main` before debugging your own diff.

## An unmeasurable quantity is `null`, never `0`

A zero and an unknown are indistinguishable once rendered, so nothing downstream
can catch the difference. This has now produced five defects in this repo
([#1480](https://github.com/pggLLC/Housing-Analytics/issues/1480)): a `0`-household
AMI band, `$0` / `-$320,000` equity, an absent Prop 123 commitment, a flat chart
line for a dead FRED series, and — most recently — `$0` resale price and owner
equity on the HNA ownership panel for **53 of 482 Colorado places** (#1531).

**`Number(null) === 0`, and `0` is finite.** That is the whole bug. A
language-level coercion turns "no data" into a real quantity that then passes
every `Number.isFinite()` check downstream and lands in front of a user as a
number they will act on.

- Do **not** apply `Number()` / `parseFloat()` / `num()` to a possibly-null value
  that then feeds arithmetic or a renderer. Guard the absence first and return
  `null`.
- Guard `<= 0`, not `< 0`, wherever zero is not a meaningful value. A purchase
  price, home value, or rent of exactly `0` means unknown, not free.
- Carry the *reason* with the data, not a label duplicated per renderer. The house
  pattern already exists — `priceUnavailableReason`, `climateUnavailableReason`,
  `demandUnavailableReason`, `hazmatUnavailableReason`, `unavailableReason`,
  `rejectedSameNameRecord`. Follow it.
- Fixing the renderer is not enough. #1478 correctly made `fmtMoney()` return
  `Value unavailable` for `null`, and the bug still shipped, because the coercion
  happened two layers upstream and the renderer never saw a `null`. Fix it where
  the value is *resolved*, and check every layer between there and the screen —
  #1531 needed three.
- A neutral default is the same defect wearing a different number. `scoreMap[x] || 50`
  scores an unrecognised category as average; `|| 60` scores an unknown hazard
  level as better than moderate. Prefer excluding the component and disclosing why.
- `npm run test:absence-static-guard` enforces the mechanically decidable forms; every safe match needs an exact allowlist entry with a durable reason.

**The broader class is not fully caught by tests, linters, or CodeQL.** The static
guard above covers three narrow forms; other instances still require a pinned
absent-case test. Prefer a repro you can run in one command over an assertion you
can only read.
